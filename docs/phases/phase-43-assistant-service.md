# Phase 43 — assistant-service

## The idea

**A product should be able to explain itself, in the user's language, without anyone writing a
manual — and it must never confidently invent an answer.**

A help assistant sits behind the `?` icon and the chat panel. It answers "what is this field?",
"how do I add a camera?", "why was my payment refused?" — grounded in a knowledge base, citing what
it used, and abstaining honestly when the KB does not cover the question.

Two things make this one different from the usual bolt-on chatbot:

1. **It retrieves.** The naive design puts the whole KB in the prompt on every request. Measured on
   a real product KB, that is **505 entries / 658,756 chars ≈ 165,000 tokens per message** for an
   admin console, and ~46,000 for a customer app. That design does not scale past a glossary, and
   it caps the KB by config to keep the bill survivable. Retrieval makes prompt size independent of
   KB size: ~8 ranked chunks, a few thousand tokens, whether the KB holds 50 entries or 50,000.

2. **The product declares itself.** Our services already publish `user_actions` / `admin_actions`,
   aggregated and capability-filtered by the gateway at `GET /api/v1/app/catalog`. The assistant
   builds KB entries from that catalog, so "what can I do here?" is answered from the product's own
   contract. It cannot drift, because the same declarations the gates enforce are the source.

## What we are replacing, and why

Studied a working implementation of this idea before designing. Its failure modes are the
requirements list, and every one is quantified or quoted rather than assumed:

| # | Observed | Consequence |
| --- | --- | --- |
| 1 | **No retrieval** — whole KB serialised into the system prompt | ~165k tokens/message at admin scale; KB frozen by a byte cap |
| 2 | **KB arrives in the request body** (≤2 MB) | The caller supplies the "truth" the assistant asserts — an injection and trust hole |
| 3 | **No citations at all** — no `sources`, no refs | "Never confidently wrong" is unenforceable; nothing to audit an answer against |
| 4 | **No tenant isolation** — user-scoped row policies only | One tenant's conversations are not isolated from another's by construction |
| 5 | **`anon:<uuid>` from a client header is a full identity** | Guess the header, read a stranger's conversations |
| 6 | **Auth decided from the request body** (an `audience` field) | Setting one body field skips token verification entirely |
| 7 | **Whole history client-supplied** (50 × 32 KB) | No server-side history, no token budget, no truncation |
| 8 | **Fail-open everywhere** | Moderation, PII redaction and encryption all default OFF; encryption silently stores plaintext when the key is missing |
| 9 | **Retention policy stored, validated, surfaced — never enforced** | A policy that exists only as a config field is a policy nobody is keeping |
| 10 | **Provider error strings returned verbatim** to the client | Upstream internals leak through a 502 body |
| 11 | **Per-user rate limit held in process memory** | Wrong the moment there is more than one replica |
| 12 | **Two UIs = two disjoint KB files** (172 and 505 entries, zero shared keys) | 22 concepts authored twice under different names, free to drift with nothing linking them |
| 13 | **Capability KB generated by a build script** that `eval`s a frontend label file | Static output, re-run by hand; its own header warns it must be re-run whenever a capability changes |

Note also that the same team's newer design document **cancels** that service and tells them to drop
its KB format and its `audience` enum. We are not copying a design its authors abandoned; we are
taking the goal and building it the way the failures above say it should be built.

## Decisions

**The KB is server-side, behind a port. It is never accepted from the request body.** A caller may
say which surface it is and what it is asking; it may not supply the facts. `KnowledgeSource`
adapters: `file`, `http`, `datastore`, `catalog` (generated from declared actions). Zero-infra
default is `file`.

**One KB, surface-tagged — not one file per UI.** An adopter may run four UIs. Entries declare
`surfaces: ["admin","web"]`, or omit it to be shared by all. The glossary is authored once. This is
the direct fix for the 22 duplicated concepts, and it makes "answers scoped to this UI only" a
filter rather than a fork of the content.

**Surface scopes relevance; capability scopes visibility.** Two layers, deliberately. A client can
claim any surface — that is a UI hint, not a credential — so an entry marked `requires:` a
capability is invisible to a caller who does not hold it. Surface alone would let a customer app
read admin help by lying about which app it is.

**One entry shape for every kind of content.** Actions are not the only thing a user asks about;
labels, glossary terms, field help, policies and FAQs matter as much. Required: `title`, `body`
(both language maps). Optional: `kind`, `surfaces`, `anchor`, `requires`, `related`. Generated and
hand-authored entries share the shape and the namespace, so nothing is special-cased.

**Two modes over one KB.** `anchor` ties an entry to a UI element, so the `?` icon does a **direct
lookup** — deterministic, no model, no latency, no cost. Questions go through retrieval and
synthesis. The same KB serves both; the cheap path is the common path.

**The model is a port, and the zero-config default still works.** `null` driver = extractive: return
the top-ranked passages verbatim with citations. The service is useful with **no API key and no
infrastructure**, like every other default in this platform. Add a provider and you get synthesis.
No vendor is baked in.

**An answer is grounded, cited, or absent.** Every claim carries the entry it came from. Below the
relevance threshold, or when retrieved evidence does not support the answer, it abstains and says
what is missing. Refusing to answer is a correct outcome, and the eval measures whether it abstains
when it should.

**It links to actions; it never performs them.** The catalog already knows what the caller may do
and where. Pointing at the right screen is nearly all the value with nearly none of the risk; acting
on a misread question is a large surface for a small gain.

**Conversations are personal data.** Tenant + subject scoped, encrypted at rest, erasable through
the standard `/internal/privacy/erase` contract, and retention is **enforced by a sweeper**, not
described in a config field.

**We ship the UI, as a web component.** An adopter with four UIs should not build the same chat
panel four times, and a backend-only help service quietly pushes that cost onto every consumer. The
service serves its own widget: one `<script>` tag, no build step, no npm dependency, no framework.

    <script src="https://.../widget.js"></script>
    <assistant-widget surface="admin" locale="ar"></assistant-widget>

A web component rather than a React package, for three reasons that each cost real money otherwise:
it works identically in React, Vue, Angular or plain HTML, so four UIs share one widget; **shadow
DOM** means the host's CSS cannot break the panel and the panel's CSS cannot leak into the host,
which is the usual first support ticket for an embedded widget; and zero dependencies keeps it
self-contained and trivial to license-audit, like everything else here.

**Branding is server-side config, per tenant and per surface** — colours, logo, assistant name,
greeting, locale, position. Set once, picked up by every UI, no rebuild. **RTL is a layout
requirement, not a translation**: Arabic mirrors the panel, and this platform targets a market
where that is the default case, not an edge case.

**The widget holds no secret, and branding cannot inject markup.** The host app mints a short-lived
token; the widget never carries an API key. Brand values are validated as colours and URLs — a
brand config that can carry HTML or CSS is stored XSS in every adopter's application, arriving
through a field nobody thinks of as untrusted.

## What must never happen

1. **A confident wrong answer.** Ungrounded or unsupported → abstain. Measured, not asserted.
2. **A caller supplying the facts.** The KB comes from a configured source, never the request.
3. **Help leaking across a capability boundary.** Admin guidance must not reach a caller who cannot
   perform it, whatever surface they claim to be.
4. **A tenant reading another tenant's conversations.** Scoped at the store, not in the handler.
5. **A prompt that grows with the KB.** Retrieval keeps context bounded and the bill predictable.
6. **A stored policy nobody enforces.** Retention runs, or it is not claimed.
7. **A secret or a person's identity reaching a third-party model.** Redaction happens before the
   outbound call, and it is on by default.

## Definition of done

- Prompt size is independent of KB size — proven by a test that indexes a large KB and asserts the
  assembled context stays within budget
- Every answer carries citations, or is an abstention
- A caller-supplied KB is refused
- An entry requiring a capability is never returned to a caller lacking it — asserted per surface
- Zero-config run works: no API key, no external service, extractive answers with citations
- Retention sweeper deletes; erasure erases; both tested
- Eval harness runs, and **a deliberately broken retriever makes it go red**
- The widget drops into a plain HTML page with one script tag and works — no build step, no
  dependency, host CSS unaffected in both directions
- A brand config carrying HTML or CSS is refused, not rendered
- All gates green, including a new one if this phase earns it

## Honest limits

- **Retrieval quality is bounded by KB quality.** If the KB does not contain the answer, the correct
  outcome is an abstention, not a better guess. We measure abstention correctness for that reason.
- **Lexical ranking alone will miss paraphrases.** BM25 is the zero-infra baseline; embeddings are
  the opt-in upgrade. We ship the baseline honestly rather than pretending it is semantic.
- **A keyword-graded eval that always passes measures nothing.** A reference eval scored 19/19 at
  100% with keyword grading; by our own rule a check that cannot fail is decoration. Ours must
  demonstrate a red run.
- **We do not promise a model never errs.** We promise grounded, cited, or absent — and that the
  gap is measured and visible.
- **Arabic ranking is harder than English.** Normalisation (diacritics, alef/ya variants) is in
  scope; full morphological stemming is not, and we will say so rather than imply parity.
